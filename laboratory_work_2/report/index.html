URL-маршрутизация в Django работает через файл urls.py. Каждый URL-паттерн связывает адрес с конкретным представлением.

Структура: в проекте есть главный urls.py (рядом с settings.py), который включает urls.py приложений:

```# urls.py проекта (blogfspo/urls.py)
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('', include('project_first_app.urls')),  
]

    include() подключает список маршрутов приложения по префиксу '' (то есть без изменений). Если бы вместо '' был указан ' app/', все адреса приложения оказались бы вложены под /app/... — сам urls.py приложения при этом менять не пришлось бы.

    Создали в приложении свой urls.py

    # urls.py приложения
from django.urls import path
from . import views

urlpatterns = [
    path('owner/<int:owner_id>/', views.owner_detail),  
]

    — конвертер типов. Django извлечёт из этой части URL целое число, отклонив запрос (вернёт 404) для нечислового значения, и передаст его функции owner_detail как именованный аргумент owner_id.

    Задание 3

    Форма — интерфейс для создания и редактирования данных. Django предоставляет класс ModelForm, который автоматически генерирует форму на основе модели: поля формы создаются из полей модели, валидация тоже берётся из модели.

    Метод is_valid() делает три вещи: проверяет заполненность обязательных полей, запускает валидаторы и сохраняет очищенные данные в form.cleaned_data. Если валидация провалилась — форма с ошибками рендерится заново, Django сам подставляет сообщения об ошибках рядом с полями.

    Я создаю файл forms.pyб нужен для того, чтобы управлять вводом данных от пользователя на сайт.

    Внутри самого класса формы CarOwnerForm вы описываете поведение формы, а внутри class Meta вы даёте Django инструкцию, из чего и как эту форму вообще собрать.

    ModelForm строит поля формы и правила валидации из полей указанной модели — отдельно описывать title = forms.CharField(...) не нужно.

    fields - Явный список полей обязателен: без него ModelForm выбросит исключение при определении класса. Перечислять все поля модели не обязательно — форма будет работать только с указанными.

    В рамках выполнения Практического задания 3 (в конце Практики 2.2) данный механизм ModelForm был применен для создания формы CarOwnerForm. В файле views.py была написана функция-представление create_owner, реализующая классический паттерн обработки веб-форм:

    1. GET-запрос: если пользователь просто открывает страницу, создается пустой экземпляр формы form = CarOwnerForm() и рендерится HTML-шаблон.
    2. POST-запрос: при отправке данных из веб-интерфейса, форма инициализируется переданными данными CarOwnerForm(request.POST). Далее вызывается метод form.is_valid(). Если валидация пройдена, метод form.save() автоматически генерирует SQL-запрос INSERT и создает новую запись автовладельца в СУБД SQLite, после чего срабатывает перенаправление (redirect) на список.

    def create_owner(request):

    Редактирование и удаление владельца

    Помимо добавления нового владельца, в приложении реализованы функции редактирования и удаления существующих владельцев.

    Для редактирования используется функциональное представление owner_update. Сначала с помощью функции get_object_or_404 из базы данных получается объект CarOwner по переданному идентификатору:

    def owner_update(request, pk):
    owner = get_object_or_404(CarOwner, pk=pk)

    if request.method == 'POST':
        form = CarOwnerForm(request.POST, instance=owner)
        if form.is_valid():
            form.save()
            return redirect('owners_list')
    else:
        form = CarOwnerForm(instance=owner)

    return render(
        request,
        'owners/create_owner.html',
        {'form': form, 'title': 'Редактировать владельца'}
    )

    При GET-запросе форма заполняется текущими данными выбранного владельца. При POST-запросе данные из формы передаются в CarOwnerForm вместе с параметром instance=owner. Это позволяет изменить уже существующий объект, а не создать новый.

    После успешной проверки данных вызывается form.save(), после чего выполняется перенаправление на страницу со списком владельцев.

    Для удаления владельца реализовано отдельное функциональное представление:

    def owner_delete(request, pk):
    owner = get_object_or_404(CarOwner, pk=pk)

    if request.method == 'POST':
        owner.delete()
        return redirect('owners_list')

    return render(
        request,
        'owners/owner_confirm_delete.html',
        {'owner': owner}
    )

    При открытии страницы удаления отображается шаблон owner_confirm_delete.html, в котором пользователь может подтвердить удаление. При отправке POST-запроса объект владельца удаляется из базы данных.

    Таким образом, для владельцев в приложении реализованы операции просмотра списка и отдельного владельца, создания, редактирования и удаления.

    Изменение данных автомобиля реализовано с помощью UpdateView:

    fields = ['license_plate', 'brand', 'model', 'color']
    template_name = 'cars/update_car.html'
    success_url = '/cars'

    UpdateView автоматически получает существующий объект Car, отображает его данные в форме и после отправки формы сохраняет изменения.

    Для редактирования используется шаблон cars/update_car.html. После успешного изменения пользователь возвращается к списку автомобилей.

    Удаление автомобиля

    Для удаления автомобиля используется DeleteView:

    class CarDelete(DeleteView):
    model = Car
    template_name = 'cars/car_confirm_delete.html'
    success_url = reverse_lazy('cars_list')

    Перед удалением отображается страница подтверждения с использованием шаблона cars/car_confirm_delete.html. После подтверждения объект удаляется, а пользователь перенаправляется на список автомобилей.

    В данном случае для success_url используется reverse_lazy('cars_list'), то есть адрес страницы определяется по имени маршрута.

Метод .strip() обрезает случайные пробелы по краям. Q(...) — это инструмент Django для сложных условий. Вертикальная черта | означает логическое или __icontains - находят строки, которые содержат аналогичные подстроки без учета регистра есть просто contains - выполняет аналогичные действия, только регистрозависимый. filter - получает набор объектов модели, которые соответствуют условию Для получения параметров из строки запроса применяется метод `request.GET.get()`, в которую передается название параметра. flight_type = request.GET.get('type', '') if flight_type in ['departure', 'arrival']: flights = flights.filter(flight_type=flight_type) Это фильтрация рейса по типу, в адресной строке мы ожидаем тип от пользователя, если в ссылке есть ?type=departure, то в переменную flight_type запишется строка 'departure'. Если в ссылке ничего нет, запишется пустая строка ''. if flight_type in ['departure', 'arrival']: Это проверка на безопасность и правильность. Код проверяет: То, что пришло из URL, это точно слово 'departure' или слово 'arrival' и пользователь вручную вставит в ссылку какую-то ерунду (например, ?type=hello или ?type=123), эта проверка не пропустит такое значение дальше. flights = flights.filter(flight_type=flight_type) Эта строчка сработает только если проверка на предыдущем шаге прошла успешно. Django берет текущий список рейсов и оставляет в нем только те, у которых в базе данных поле flight_type (тип рейса) в точности совпадает со значением из URL. paginator = Paginator(flights,4) page_number = request.GET.get('page') page_obj = paginator.get_page(page_number) query_params = request.GET.copy() if 'page' in query_params: query_params.pop('page') Пагинация необходима для разделения длинного списка на страницы. paginator = Paginator(flights,4) - разбиваем все рейсы по 4 штуке на странице page_number = request.GET.get('page') - узнаем какую страницу хочет увидеть пользователь, Если пользователь нажал на кнопку 2, то URL будет выглядеть как ?page=2, и в переменную page_number запишется строка '2' page_obj = paginator.get_page(page_number) query_params = request.GET.copy() - Мы копируем все текущие параметры поиска (город, дату, сортировку), но удаляем из них сам номер страницы (page). Чтобы в HTML-шаблоне при клике на Следующая страница ссылка выглядела как ?q=Москва&date=2026-10-31&page=2. Если этого не сделать, при переходе на другую страницу поиск по Москве просто сбросился бы if 'page' in query_params: query_params.pop('page') ``` Удаляем старый номер страницы из этой копии. Метод urlencode() превратит этот словарь в готовую строку параметров.

    login_view

    def login_view(request):
    if request.method != 'POST':
        return render(request, 'flights/login.html')

    username = request.POST.get('username', '').strip()
    password = request.POST.get('password', '')

    user = authenticate(request, username=username, password=password)

    if user is None:
        messages.error(request, 'Неверный логин или пароль.')
        return render(request, 'flights/login.html')

    login(request, user)
    return redirect('home')
